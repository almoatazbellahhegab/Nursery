Purpose and Enforcement
These standards apply to the administration portal, Flutter application, Python services, database, infrastructure and automated tests. They are mandatory for new code. A deviation requires a short architecture decision or pull-request explanation, named approval and a remediation plan when the deviation is temporary.
The objective is readable, secure and testable software. Comments and documentation must help a future developer understand intent, business rules, trust boundaries and non-obvious behavior. They must not create noise by repeating syntax that is already clear from the code.

General Coding Rules
☐ Use small cohesive modules with one clear responsibility and explicit public interfaces.
☐ Use descriptive domain names. Avoid abbreviations that are not present in the product vocabulary.
☐ Validate data at every trust boundary and represent validated data with typed objects.
☐ Keep functions short enough to understand without scrolling through unrelated responsibilities.
☐ Prefer explicit control flow over clever expressions, reflection or hidden framework behavior.
☐ Represent business states with enums or state objects and validate transitions centrally.
☐ Use UTC for stored instants and organization timezones only for interpretation, scheduling and display.
☐ Use integer minor units and a currency code for money. Never use binary floating point for balances.
☐ Do not ignore errors, catch broad exceptions without classification or return a success response before durable completion.
☐ Do not add an abstraction until it removes demonstrated duplication, establishes a security boundary or represents a stable domain concept.
Comment and Documentation Standard
Every part of the codebase must be understandable, but that does not mean commenting every line. Code explains what happens; comments explain why it happens, which invariant is protected, what is intentionally excluded and what failure or policy concern a future change must preserve.

Comment Rules
Place a short orienting comment before a non-obvious block, not after each line inside it.
Document business-policy provenance with an approved requirement, feature, ADR or policy identifier where available.
Document temporary compromises with an issue identifier, owner and removal condition. Unowned TODO comments are prohibited.
Update or remove comments in the same change that modifies the behavior they describe.
Never place credentials, tokens, personal data, child names or production examples in comments.
Do not comment obvious assignments, standard framework calls, closing braces or code whose name already states the behavior.

Python Standards
Use the supported Python release selected for the project and pin dependencies with a reproducible lockfile.
Use FastAPI only at transport boundaries, Pydantic for external schemas and explicit domain or application services for business behavior.
Use complete type annotations for application code. CI runs mypy in strict or an approved progressively strict configuration.
Use Ruff for linting and formatting, pytest for tests and a dependency vulnerability scanner in CI.
Controllers validate transport data, establish request context and call one application use case. They do not contain SQL or multi-step business policy.
Repositories expose domain-oriented operations and always require an explicit organization or trusted platform context.
Use explicit transaction boundaries in application services. Do not commit from repositories or helper functions.
Catch specific exceptions at the layer that can translate or recover from them. Preserve causal context and expose safe error codes.
Async functions must not call blocking network or disk libraries on the event loop. Use supported asynchronous drivers or bounded executors.
Flutter and Dart Standards
Use feature-oriented packages with presentation, application and data boundaries. Widgets do not call HTTP or SQLite directly.
Use immutable typed models, exhaustive states and generated serialization from the reviewed OpenAPI contract where practical.
Run dart format, flutter analyze and the approved lint configuration in CI.
Store authentication secrets only in platform secure storage. Store approved offline data in encrypted SQLite and clear it on logout, revocation or policy expiry.
Represent loading, pending sync, conflict, failure, empty and success as distinct visible states.
Use semantic labels, scalable text, large touch targets and direction-aware layouts. Do not hardcode left and right where start and end express the intent.
All user-visible strings come from Arabic and English localization catalogues. Concatenating translated fragments is prohibited.
Offline commands retain a stable operation ID and must not be removed until the server confirms success or returns an actionable terminal response.
TypeScript and Next.js Standards
Enable TypeScript strict mode. The any type requires a localized justification and an issue when temporary.
Run ESLint, Prettier, type checking and unit tests in CI.
Prefer server-rendered or server-owned data loading for administrative pages where it reduces exposed state, while preserving responsive interactions.
Generated API types are authoritative at the transport boundary. Convert them into view models when presentation needs differ.
Components do not implement authorization. They may hide unavailable actions for usability, but the API remains authoritative.
Use accessible HTML semantics, keyboard behavior, focus management and direction-aware CSS. Validate Arabic content and mixed-direction identifiers.
Do not place secrets in browser bundles, public runtime configuration or client telemetry.
Use bounded, cancellable data requests and distinguish authorization, validation, conflict, unavailable and unexpected failures.

Authorization Coding Rules
☐ Read identity from the validated server request context, never from body or query fields.
☐ Load membership, assignments and relationships from authoritative storage or a short-lived invalidation-safe cache.
☐ Check organization state and tenant equality before returning whether a referenced resource exists.
☐ Apply action policy and field filtering separately. Permission to view a record does not imply permission to view every field.
☐ Pass organization context into every repository call and establish database row-security context inside the same transaction.
☐ Do not create administrator bypass helpers. Exceptional support access requires an approved support context and audit event.
☐ Add positive and negative tests whenever a policy changes, including a neighboring role, branch, classroom and organization.
Database and Migration Standards
Every tenant table contains organization_id, suitable indexes and approved row-level policies.
Use database constraints for required fields, uniqueness, valid references and simple invariants. Application validation does not replace database integrity.
Use Alembic revisions with deterministic upgrade steps. A committed migration is immutable after it is used by a shared environment.
Apply expand, migrate and contract for breaking changes. Backfills are restartable, observable and bounded by primary-key or cursor ranges.
Never perform a long unbounded data rewrite inside a normal deployment transaction.
Migration reviews state lock risk, table size assumption, compatibility, validation query, expected duration and recovery approach.
Row-level security policies, grants and tenant constraints receive integration tests against a real PostgreSQL instance.
Audit, payment and safety history must not be silently updated or deleted. Corrections append a superseding record where the model requires immutable history.
Asynchronous and Integration Standards
Publish external work through a transactional outbox when it depends on a committed business change.
Every consumer is idempotent and safe under duplicate, delayed and out-of-order delivery.
Queue messages contain identifiers and minimal routing metadata, not unnecessary child or medical content.
Set bounded retries with exponential backoff and jitter. Permanent failures go to a dead-letter queue with an owner and runbook.
Verify webhook signatures, timestamps and replay protection before parsing provider claims into domain events.
Wrap vendors behind internal adapter interfaces and test each adapter against provider-independent contract fixtures.
Configure explicit connection, read and total timeouts. Do not allow an external provider wait to hold a database transaction open.

Security Standards
☐ Threat-model each new trust boundary, sensitive workflow or external integration.
☐ Use least-privilege IAM roles per service and environment. Human production access is time-bounded and audited.
☐ Encrypt data in transit and at rest. Use managed secret storage and automated rotation where the provider supports it.
☐ Use parameterized queries and framework escaping. Review every raw SQL, HTML injection and file-path operation.
☐ Validate file signature, type and size; quarantine and scan uploads before availability.
☐ Apply rate limits and abuse controls to authentication, invitations, search, messaging, uploads, QR or PIN attempts and exports.
☐ Use secure headers, CSRF protection where applicable, restrictive CORS and short-lived signed media access.
☐ Run secret, dependency, static-analysis, container and infrastructure scans in CI and triage findings by defined SLA.
☐ Complete independent security review before production launch and after material identity, payment, pickup or media changes.

Name tests as observable behavior under a condition, for example denies a teacher from an unassigned classroom.
Use deterministic fixtures with clearly separated organizations, branches, classrooms, relationships and roles.
Every allowed-path test for sensitive data has a corresponding denied-path or filtered-field test.
A defect fix includes a failing regression test at the lowest useful level and broader coverage when the defect crosses a boundary.
Do not mock PostgreSQL behavior when testing transactions, SQL, constraints or row-level security.
Flaky tests are defects. Quarantine requires an owner, issue, expiry and preserved release coverage.
Pull Request Standard
☐ The change is limited to one coherent outcome and links its feature, defect, ADR or operational need.
☐ The description explains behavior, security or data implications, tests, migration, rollout and rollback.
☐ Public interfaces, complex logic and security invariants have useful documentation and current comments.
☐ Tests cover allowed, denied and failure paths appropriate to the change.
☐ No secrets, production data, sensitive logs, generated noise or unrelated formatting changes are included.
☐ API, database, localization, accessibility and observability impacts are reviewed where applicable.
☐ At least one qualified reviewer approves; security, database, finance or safeguarding owners review changes in their governed areas.
☐ All required CI checks pass and unresolved review conversations are closed with evidence.

Definition of Ready
☐ Outcome, acceptance criteria and non-goals are understood.
☐ Dependencies and policy gates are satisfied.
☐ UX covers success, empty, loading, validation, denied, offline, conflict and failure states as applicable.
☐ Authorization, data classification, audit and retention implications are reviewed.
☐ API, event, migration and integration contracts are defined.
☐ Test cases, telemetry, rollout and rollback are defined before implementation begins.
Definition of Done
☐ Feature and cross-cutting acceptance criteria pass, including denied and edge paths.
☐ Code follows these standards and has current, useful documentation and comments.
☐ Automated tests, security checks, localization, RTL and accessibility validation pass at the appropriate levels.
☐ Migrations, observability, dashboards, alerts, runbooks, rollout and rollback are complete.
☐ Sensitive actions are auditable and logs contain no prohibited data.
☐ Product, Design, QA and required specialist owners complete validation.
☐ Known limitations, release notes and support guidance are updated.
