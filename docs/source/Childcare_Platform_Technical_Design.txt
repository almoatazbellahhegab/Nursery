Executive Summary
Decision: Build the initial platform as a modular monolith with a Next.js and TypeScript administration portal, a Flutter mobile application, a Python FastAPI API and worker runtime, PostgreSQL as the authoritative system of record, and managed AWS infrastructure. This design minimizes operational complexity while preserving replaceable integration boundaries for identity, notifications, media, payments and future external APIs.
The architecture prioritizes child safety, tenant isolation, auditable authorization, offline-safe classroom entry, financial integrity, Arabic and English support, and recoverable asynchronous processing. It intentionally avoids microservices, Kubernetes, Kafka, a separate search cluster and a data warehouse until measured demand justifies them.

Problem Definition
Give childcare centers one system to manage children, parents, staff, attendance, daily activities, communication, billing, pickup authorization, and parent engagement.
The platform must serve multiple childcare organizations and branches from one configurable product. It must support high-frequency care workflows, guardian engagement and sensitive operational records without allowing cross-organization, cross-branch, unrelated-child or inappropriate field access.
Goals
Operate one complete childcare day in Arabic and English using responsive web and mobile experiences.
Enforce organization, branch, classroom, assignment, guardian relationship, consent, role and task-purpose boundaries on the server.
Preserve correctness across retries, concurrency, short connectivity failures and asynchronous delivery.
Protect medical, identity, incident, pickup, payment and media information throughout its lifecycle.
Provide auditable administration, support access, configuration, deployment and recovery.
Keep payment, notification, identity and media integrations replaceable without redesigning core domain logic.
Non Goals
Full payroll, leave management, and advanced shift management.
Real-time vehicle location tracking.
Parent social community and parent-to-parent messaging.
Commerce catalog, fulfillment, platform commissions, and marketplace operations.
Dedicated app-store builds, custom domains, and public integration APIs.
Medical diagnosis, treatment recommendation, or clinical decision support.

Identity and Authorization

Authorization evaluation sequence for every protected request
Authentication
Cognito authenticates email, phone and approved social identities through standards-based OIDC flows.
Administrators and platform support roles require MFA. Sensitive support access and designated high-risk actions require recent or stepped-up authentication.
The API validates issuer, audience, signature, token lifetime and required authentication strength. It never trusts role, tenant or child access supplied by the client.
Account linking follows a verified invitation or administrator-controlled process to prevent accidental or malicious identity merging.
Suspension is checked against authoritative application state on every protected request, not only when a token is issued.
Authorization Model
Authorization combines role capabilities with attributes and relationships. A request is permitted only when the account, organization and membership are active; the role permits the action; the branch and classroom scope matches; any required child assignment or guardian relationship exists; consent and field rules allow the data; and the requested purpose is appropriate.

Use UUIDv7 or an equivalent sortable, globally unique identifier generated by trusted application code.
Use UTC instants for persisted event times and retain the relevant organization timezone for interpretation and display.
Use integer minor units plus ISO currency codes for money. Floating-point types are prohibited for financial amounts.
Use explicit lifecycle states and transition services. Do not infer business state from nullable timestamps alone.
Use tenant-aware unique constraints and foreign keys so an identifier from one organization cannot be attached to another organization.
Prefer append-only events for attendance corrections, payments, consent, incidents and audit history; corrections reference the superseded record.
Tenant Isolation
All tenant-owned tables include organization_id. The API opens a transaction, establishes a transaction-local tenant context, performs application authorization and executes through a restricted database role. PostgreSQL row-level policies then provide a second denial boundary. The runtime role must not own protected tables and must not have BYPASSRLS. Platform-wide operations use separate, explicitly reviewed repositories and service methods.
☐ Every tenant table has row-level security enabled and forced where appropriate.
☐ Every tenant query has an organization predicate even when row-level security also applies.
☐ Cross-organization foreign keys are impossible through composite or validated tenant keys.
☐ Exports, search, reports, media paths, notifications and worker jobs receive the same isolation tests as ordinary API reads.
☐ Database migration and administrative roles are never used by the application runtime.
API and Contract Design
Expose versioned HTTPS REST resources under /api/v1 and publish an OpenAPI contract from FastAPI.
Generate Dart and TypeScript clients in CI. Generated clients are committed or packaged with a repeatable generation command and compatibility check.
Use cursor pagination for ordered, frequently changing lists. Use bounded offset pagination only for stable administrative views where direct page navigation is required.
Accept an Idempotency-Key for retryable creates and safety or financial commands. Store request fingerprint and result for the defined replay period.
Use ETag or explicit version fields for mutable records where concurrent updates must be detected.
Return stable machine-readable error codes, a user-safe localized message key and a correlation identifier. Never disclose record existence across an authorization boundary.
Use UTC ISO 8601 timestamps, ISO currency codes and locale-neutral wire values. Localization occurs at the client or notification rendering boundary.
Offline Synchronization
Offline capability is limited to approved basic attendance and care entry. The client does not download a full organization database. Each queued command carries a stable client operation ID, organization, actor, subject, device time, server-known version and payload schema version.
Write the local event and outbox command in one SQLite transaction.
When connectivity returns, send commands in bounded batches using the authenticated user's current session.
The API re-evaluates authorization and organization state, validates the command and records the operation ID with the resulting server record in one PostgreSQL transaction.
A repeated operation ID returns the original result without creating a duplicate.
Non-conflicting events append normally. Mutually exclusive state changes use explicit conflict rules and return a conflict object rather than silently selecting a winner.
The client marks confirmed commands complete, displays rejected commands with a recovery action and securely removes expired local data.
Asynchronous Processing
The API writes a domain change and an outbox record in the same PostgreSQL transaction. A relay publishes pending outbox records to SQS. Workers acknowledge messages only after durable completion or a safely recorded terminal outcome. Consumers remain idempotent because standard queues may redeliver.

Media Design
Clients request a short-lived upload authorization after the API confirms role, organization, child scope and media purpose.
Uploads enter a private quarantine prefix. Workers validate type and size, scan for malware, remove unnecessary metadata and generate approved derivatives.
The database stores the asset, organization, uploader, children shown, consent purpose, processing status and object references.
Downloads require a fresh authorization and consent evaluation before the API issues an expiring signed URL or cookie.
Revoked consent blocks future access and schedules policy-approved deletion or restriction; CDN caching must not outlive authorization assumptions.
Public object ACLs are prohibited. Storage and access logs must not contain child names or sensitive metadata.
Notifications and Messaging
Notification creation, audience selection and channel delivery are separate concerns. Domain modules request a notification using a stable event and template key. The notification module resolves mandatory versus optional categories, current guardian relationships, preferences, locale and quiet-hour rules before creating channel deliveries.
Use versioned Arabic and English ICU templates with review ownership and test fixtures.
Do not place medical, incident, financial or pickup secrets in lock-screen notification text.
Mandatory safety notices cannot be disabled but still require policy-approved wording and escalation behavior.
Track accepted, delivered, failed and opened states only where the provider reliably supports them; do not present accepted as delivered.
Store message attachments privately and evaluate conversation participation on every read and send operation.
Payment Boundary
The payment provider remains undecided. The revenue module owns invoices, balances, allocation and reconciliation. A provider adapter owns checkout creation, provider-specific credentials, signature verification and event translation. The browser or mobile response is never authoritative proof of payment.
☐ Approved market, payment methods, tax, receipts, refunds, reversals and disputes are defined.
☐ Provider webhook signatures and replay windows are verified.
☐ Provider events are immutable, deduplicated and mapped to internal payment events.
☐ Invoice balance updates and payment event recording occur atomically.
☐ Daily reconciliation identifies missing, duplicated and mismatched provider transactions.
☐ Provider replacement tests run against the internal adapter contract.
Search and Analytics
MVP administrative search uses PostgreSQL indexes, full-text search and trigram matching with the same tenant and permission filters as the underlying records. Search results return minimal summaries and require ordinary authorization to open. Analytics begin with defined SQL projections and materialized aggregates; a separate search engine or warehouse is introduced only after measured query or retention needs justify it.

Privacy and Data Lifecycle
Classify fields as public business, internal, personal, sensitive child, medical, safety, financial, credential or audit data.
Collect optional fields only for an approved purpose and retain the legal basis or consent version when required.
Represent access revocation, archival, legal hold, deletion request and physical deletion as explicit lifecycle states.
Organization exports run asynchronously, are scoped and audited, produce encrypted short-lived files and never combine tenants.
Deletion workflows identify dependent records, statutory or safeguarding retention, media copies, derived assets, queues, caches, backups and audit integrity.
Production data is prohibited in development and test environments. Demo data is synthetic and visibly marked.
